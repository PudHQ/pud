# What could Pud be?

## Decision

**Ship a TypeScript contract runner. Pilot a debugger as a way into it.** A team that knows what must hold can commit the guarantee beside the source and check it on every edit. For the team that only has a surprising call, test whether answering a question about the real export earns the effort of adopting a rule. Build and evaluate the debugger separately. Sharing source resolution and replay reduces its cost, but finding an informative alternative input is its own engineering problem.

The distinction matters on day one. Suppose a support ticket says a grandfathered account with 12 units used can export four more but cannot export five. A debugger can reproduce the boundary immediately. It cannot tell the developer whether 16 is the right quota. A rule approved from the plan terms can settle that question and catch a different mistake next month. The product hypothesis is that going from a question to a lasting guarantee is valuable enough to earn a place alongside the team's test runner.

**My strongest alternative is a checked codemod.** It delivers a safe part of a migration and a concrete explanation for the sites it leaves alone. A team can get value without first adopting a specification practice. **My longer-term bet is behavioral compatibility for dependencies.** Start on the consumer side where one app already knows what it relies on. Publishing proofs with npm packages becomes interesting after consumers want to check them.

The earlier [alpha recommendation](recommendation.md) and [26 workshop pitches](README.md) remain available. The pitches mixed proposed products, implementation techniques and example workloads. The designs below are compared by what a team **adopts**, what Pud **produces**, and what would make a claim **credible**. They share techniques. Their value and cost can differ even when the underlying checker is identical.

## What the developer actually writes

Consider one promise throughout: for nonnegative usage and a positive batch, `admit(used, batch)` returns true exactly when `used + batch <= 16n`.

| Authoring setup | What appears in review | Engineering commitment |
| --- | --- | --- |
| Inline LemmaScript annotations | In `quota.ts`, a `requires` clause and `//@ ensures \result === (used + batch <= 16n)` beside the body. | Extract the actual annotated declaration and its dependencies. Easy to find when editing the function. |
| Ordinary TypeScript sidecar | `quota.proof.ts` imports `admit`. Its predicate compares the actual result with `used + batch <= 16n` under the reviewed precondition. | Preserve TypeScript inference and source binding. Explain exactly which callback expressions the checker supports. |
| Zod-style property language | Declare symbolic integer arguments and `.returns(used.add(batch).lte(16n))`. | The builder produces a translatable expression tree. Pud owns the meaning of every operator. A return schema of “boolean” would admit both answers. |
| Bridge to a native theorem | The sidecar links the export and reviewed claim to `Quota.v#admit_correct`. The agent writes the Rocq proof. | Regenerate the theorem's expected type from the real TS. Validate assumptions and reject stale or unrelated proofs. |
| Dedicated spec language or prose-assisted authoring | A `.pud` file says `result iff used + batch <= 16`. Alternatively an owner writes a sentence and reviews the formal statement an agent derives from it. | A DSL needs deterministic semantics. Prose needs a checked-in interpretation. Regenerating that interpretation silently would let an agent change the guarantee. |

These can compose. My default is a typed sidecar with named predicates and an agent drafting the first version. I would trial LemmaScript behind it before building another broad translator. In the measured quota case, LemmaScript handled a module constant that Pud's frontend rejected. That measures extractor coverage. It tells us nothing about whether engineers prefer comments or sidecars. The [technical setups comparison](technical-setups.md) gives complete examples, alternative bindings, and a multi-rule allocation problem that a pleasant quota snippet can hide. [Measured quota trial](../prover-comparison/quota.md)

## Eighteen possible releases

Each proposal has a deliverable somebody could adopt. Several could eventually be features of one release. The count describes these designs. It carries no weight in choosing a winner. Commands and APIs are sketches. The case studies are identified where we have run them.

### Tools that help someone decide what the code should do

**1. A contract runner for existing TypeScript.** A developer imports the real export into `quota.proof.ts`, approves the relation above, and runs `pud.dev`. On a strict-boundary mistake it reports `admit(12n, 4n) → false, expected true`. The asset that survives the PR is the business rule. The hard part is faithfully covering the team's actual TS. Compare with writing the same assertion over the same domain in Vitest. If the team spends the same time and makes the same decisions, a separate runner earns little.

**2. A reviewer for specifications.** A team already has green contracts. On an edit to one of them, `pud.dev diff` returns an answer that became legal. In the outage-credit study the actual app pays $10 at minute 60 on both revisions. The policy changed from permitting $10 or $15 to permitting $5 or $10. This tool can be useful before any implementation changes. It must consider the other active promises: requiring equal credit throughout the five-minute bucket rules out the apparent $5 alternative. The product succeeds if owners regularly catch material changes to policy by reading one such example. [Rule-diff study](study-rule-diff.ts)

**3. A policy compiler.** The app imports its decision from a versioned plan table or a small policy language. A product engineer changes the legacy limit to 16. Pud checks the table for missing or conflicting decisions, then produces the TS function used at checkout. A second handwritten implementation disappears. The adoption cost is real: teams must route production decisions through a compiler they trust. Trial this against extracting the same rule into a plain, reviewed TS module. A compiler error or miswired plan lookup can affect every caller.

**4. A coding tool that owes the user a proof.** An agent receives `implement(admit)` with a fixed signature and approved postcondition. Its deliverable is a patch plus independently checkable evidence. It may choose among correct algorithms, and on a failed attempt the checker returns a case or an unfinished obligation. This differs from a CI runner in the work the agent performs before opening the PR. The test to beat is the same agent, same time budget and ordinary feedback. Seed a weak postcondition as well as a wrong implementation. An agent that reliably satisfies the wrong brief is a poor product.

**5. A build tool for proof artifacts.** A team that already uses Lean, Rocq or Dafny brings its native files. Pud resolves which TS sources, theorems and assumptions changed, rechecks the affected bindings and emits a reviewable build receipt. The developer buys reproducible linking and incremental builds. The tool's worst mistake would be accepting a proof about a hand-written model after the deployed export changes. Compare setup and repair effort with running the existing provers from a build script. This serves teams willing to maintain formal artifacts, a narrower audience than the everyday SaaS developer.

### Tools that produce something useful on an ordinary workday

**6. A counterfactual debugger.** Select a denied request in the editor. Lock the account and usage, vary the batch, and ask “what is the smallest edit that would change this answer?” With 12 units used and a rejected batch of five, it can replay four and show the accepted return beside the refusal. The first result needs no permanent spec. Claiming *smallest* requires a distance measure and enough search to establish minimality. Compare with a breakpoint and a coding agent on an unfamiliar real export. The second use tells us whether this is a product or a good onboarding interaction.

**7. A fixture generator for hard-to-reach code.** Point at a branch in a real handler and run `pud.dev reach`. Get the request, database rows and setup sequence that actually reach it, ready for an existing test. Working backwards from a branch can save more time than generating random payloads which fail the first validator. A candidate fixture earns its place by replaying through the real entry point and migrations. A budget timeout leaves reachability open. Measure time to a usable fixture against the team's own factory helpers and agent. This tool can succeed even for customers who never keep a proof file.

**8. A checked codemod.** A maintainer needs to replace a rounding operation across dozens of call sites. Pud applies the rewrite wherever it can establish the necessary precondition and leaves a source-located counterexample or an unresolved site everywhere else. Changing `Math.floor(cents / 2)` to `Math.trunc(cents / 2)` agreed on the examples −4, 0 and 4 cents. Over integer cents −5 through 5 it changed payouts at −5, −3 and −1. A nonnegative charge and a signed adjustment therefore deserve different patches. Our experiment enumerated supplied domains. A product has to infer or discharge each call site's actual domain, including exceptions and observable effects. Compare the resulting patch with a conventional codemod plus review. [Runnable comparison](study-proof-tools.ts)

**9. A test retirement assistant.** Run `pud.dev retire quota.test.ts` after a team adopts a lasting quota rule. It identifies the assertions that follow from that rule and proposes a small deletion diff. A case that also checks a receipt, an exception or HTTP wiring stays. Preserve the reason for each deletion so a later weakening of the rule reopens the lost coverage. Otherwise the tool can make the suite look healthier precisely when it has lost a guarantee. Measure accepted deletions, missed assertions and later regressions against a human cleaning up the same suite. This directly addresses the promise “proofs replace some tests.”

**10. A compiler for safe cache keys.** A developer marks a pure decision as cacheable and proposes `key: request => request.used`. Pud must establish that equal keys always give the same observed answer before enabling reuse. In the quota fixture, 13 units used and batches of one and four collide but return opposite answers. Over all 2,278 unordered pairs of distinct requests, that key had ten conflicts. Keying by `used + batch` had zero for the declared domain and the boolean result. A live entitlement service would also have to account for plan, policy revision and mutable state. The product would ship the approved cache policy. Compare its hit rate and checking cost with using a conventional complete key. [Runnable comparison](study-proof-tools.ts)

We also tested the core of that product symbolically. LemmaScript and Dafny verified that equal totals give equal results for **every** nonnegative usage and positive batch in the extracted integer model. The usage-only variant failed its postcondition. The generated unit contained the quota function and the comparison, and native execution supplied the concrete conflict. This is one case where a new developer tool could use existing translation work today. [Reproduce the two-call proof](technical-setups.md#can-a-real-checker-already-handle-a-rule-about-two-calls)

### Tools that know about transactions, time or actual customers

**11. A deterministic workflow explorer.** Run two genuine request handlers against controlled database connections. Pause both after they read the last two units. Choose which commits and which retries. The output is a replayable schedule showing an overgrant or double consumption. Enumerating a bounded set of schedules earns a bounded claim. The app's actual isolation, clocks, transactions and provider acknowledgments matter. The adoption test is whether an independently chosen inventory handler works with Pud's stock adapter. Needing a second implementation of the handler defeats its purpose. [Current database experiment and scope](../debit-endpoint/README.md)

**12. A transactional resource library.** The app adopts `quota.consume(account, units, requestId)`. Pud owns the authoritative counter, atomic admission and durable, single-use grant. The export worker consumes that grant. The developer buys an invariant enforced on the write path and may never open a proof file. An alternate writer, reusable grant, or gap between committing the grant and dispatching work can invalidate the promise. Compare with a small SQL procedure and transactional outbox. This design has a higher operational burden because Pud participates in production availability.

**13. A release checker powered by the team's own reconciliation.** A billing team already knows how to recompute usage from the ledger. On a PR, Pud runs the real update, waits for the matching settled revision and compares affected records against the rebuild. The first useful output is “project A still shows 30 minutes; the ledger says zero.” A disagreement unrelated to this change should remain distinguishable. This works when the reference is independent, keyed correctly and complete. Compare against one integration assertion around the same existing audit. [Reconciliation study](study-rebuild.ts)

**14. A customer impact query for releases.** Product or support asks “who will be denied by this change?” Run old and new TS against the same pinned, authorized account snapshot. Produce the affected account set, the two decisions and a replay a reviewer can inspect. This answers a population question a universal counterexample cannot answer. Wrong joins, stale usage or missing accounts can produce a convincing, incomplete list. Start by running both exports directly. A database-compiled query earns its complexity only when its equivalence and speed matter at the team's data volume.

**15. A cross-version rollout planner.** A new event writer can emit `quota_granted` before older workers know how to read it. `pud.dev rollout` takes the readers, writers, supported versions and durable event shapes. It returns a feasible deployment sequence or a retained event that makes rollback unsafe. The unit of work is a release across services. Correctness depends on the actual mixed-version deployment and queue retention assumptions. The incumbent is a compatibility matrix plus an expand/contract playbook. Pilot this where a platform team already spends engineering days coordinating such releases.

### Tools that let someone rely on work done by someone else

**16. A behavioral dependency gate.** An app commits the assumptions it makes about a billing package. On upgrade, Pud checks them against the candidate package's actual entry point and supplies a breaking call. That consumer-only version can ship immediately for supported code. The larger version lets publishers attach machine-checkable proofs to packages, so multiple consumers can verify guarantees cheaply. Bind any certificate to the installed bytes, relevant conditional exports and semantics. A signed statement that CI passed only identifies the signer. Try real dependency upgrades before committing to a two-sided registry.

**17. A checker for answers produced by an AI or optimizer.** A scheduling service can use any algorithm it wants. With each proposed schedule it submits an assignment and a certificate giving an upper bound on how many appointments can be filled. A small checker verifies feasibility and that the result reaches the bound before the app publishes it. Multiple schedules can earn acceptance. This checks the current answer even when the generator is opaque. The hard question is whether the certificate is cheaper to check than independently recomputing the result. Compare both on the same workloads. [Scheduling study](study-matching.ts)

**18. A verified standard library for SaaS.** A developer imports a reviewed money splitter, quota primitive or interval calculator. Each version ships an executable implementation, a precise policy and source-linked guarantees. The developer gets an answer by replacing code with a dependency. For weighted allocation, a useful catalog must tell them whether their chosen method allows a recipient to lose a unit when the pool grows. An impeccably verified algorithm with the wrong rounding policy still makes the wrong payment for this customer. Pilot one primitive against the team's existing library. Require evidence of repeated adoption before assembling a catalog. [Allocation study](study-allocation.ts)

## Which of these belong together?

| Bet | Where it could win | What would change my mind |
| --- | --- | --- |
| **Contract runner, with a debugger as a possible first encounter** | A TS engineer can try it on today's function and keep protection for the next agent edit. Rule review answers a question the test suite can leave open. | If owners cannot cheaply assess the generated rule, green checks are cheap to produce and hard to trust. If teams keep using the debugger but never keep a rule, investigate it as a standalone tool. |
| **Checked codemod** | A mergeable partial patch makes the benefit visible. Repeated migrations across repos support a distinct buyer. | A codemod that needs blanket integer, purity or caller assumptions is a slow way to produce the patch a human already wrote. Measure accepted safe sites, wrongly changed sites and total review time. |
| **Consumer-side dependency checks** | A platform team can verify what its own app relies on before upgrading. Evidence can eventually move across company boundaries. | If normal consumer tests and migration notes already resolve almost every material upgrade decision at the same cost, the shared proof infrastructure has little to sell. |
| **Workflow exploration and reconciliation** | These include real DB behavior, which the stated Pud ambition needs. The team provides its migrations, handler or existing reference. | The first stock adapter that needs a hand-built twin of each app has failed portability. An observed replay and a proved transaction invariant should each remain usable on their own terms. |
| **Policy compiler, resource library or verified standard library** | These are strong alternatives for teams willing to move production logic into a dependency. A reviewed implementation can remove duplicated code, rules and tests. | Requiring a production migration merely to evaluate a proof is a high price for this audience. Prefer this family only when replacing the decision or the write path is already a goal. |

Some pairs deserve a common engine and separate experiments. A debugger and fixture generator can share a search engine, but one returns an explanation and the other a setup a test can execute. A cache checker and dependency gate can share a comparison of two behaviors, but one controls live response reuse and the other controls an upgrade. A browser UI, a Vitest reporter or an extra prover becomes valuable only where it improves one of these jobs.

**Who would choose to pay?** For the local runner, first earn a place in a developer's repo. A platform team has a separate reason to pay if shared CI execution, reusable evidence or cross-repo guarantees save more than running the open checker itself. For codemods, a migration owner can measure engineer-days per accepted rollout. For dependency compatibility, a platform lead can measure how many upgrade investigations it eliminates. For the resource library, the buyer must also accept an availability dependency on Pud. These are distinct commercial hypotheses. The first pilot measures developer pull before any hosted service becomes necessary.

## What the first release would commit us to

- **Public interface.** One `pud.dev` command and a typed `check()` result available to Bun or Vitest. The runner takes an imported export and a rule. The experimental debugger takes an export, a real call and the inputs the developer allows it to vary. Neither path asks for a solver choice. An exhausted search says which inputs it inspected.
- **From observation to guarantee.** The debugger can save “12 used plus four succeeds” as an example. The agent can propose “for every positive batch and nonnegative usage, admit exactly when the sum is at most 16.” The owner inspects both 12+4 and 13+4 and approves that formula against the plan terms. On the next PR, somebody accidentally denies 9+4. The saved example still passes. The reviewed rule catches the regression. This is the interaction to test against using a debugger and a test runner separately.
- **Truth in the report.** “This call returned false” requires a real replay. “All 68 calls in this domain agree” requires complete enumeration under controlled inputs and execution. A symbolic theorem describes its input model, source binding and assumptions. A finite search that timed out stays inconclusive. A policy diff showing that $5 is permissible must distinguish that from an actual $5 payout. These distinctions should survive every future backend swap.
- **Technical scope.** Own export resolution, dependency tracking, rule identity, observations and receipts. Use the TypeScript compiler and a small admitted deterministic fragment. Try pinned LemmaScript/Dafny where symbolic coverage pays. Reuse the existing Rocq bridge when a native proof is actually needed. A handwritten theorem or model must never quietly stand in for unsupported source code. State and concurrency need independent adapters and evidence.
- **LLMs.** Let them propose rules, contrasting examples, implementations and proof repairs. CI checks approved inputs deterministically. When the same agent changes code and its expected result, make the changed contract visible. Choosing between two outputs is evidence about one case. The broader rule deserves its own review.

## The decision experiment

**Test entry and retention separately.** On six unseen modules from three TS teams, counterbalance three workflows on matched changes. Give each team its current test runner with the same agent, a Pud debugger starting from a real call, and Pud starting from an agent-drafted sidecar. Include an equivalent refactor, a boundary defect, a genuinely unsupported effect and a spec edit that silently permits a wrong answer. Independently label the correct review decision. Count setup failures and all authoring and review time. Later introduce a *different* regression to test whether the saved artifact helps on the second edit.

Apply the [existing adoption gate](recommendation.md#what-to-fund-next) to the runner. Record actual opportunities and unprompted reuse. Evaluate the debugger on first correct diagnosis and on how many discoveries become useful lasting rules. If the library wins but teams invoke it from Vitest, ship that integration. If the existing suite matches it for accuracy and effort, there is little reason to install another runner.

**Give the codemod its own trial.** Pick one real repetitive migration with arithmetic or normalization behavior the owner can independently judge. Run Pud and the team's usual codemod on held-out call sites, including a legitimate signed-input exception. Have the maintainer assess patches blind. Count unsafe edits, safe edits unnecessarily withheld and time to an accepted patch. If this saves substantial review time while the contract pilot fails to earn a second use, pivot to checked migrations.

**Make database portability the next engineering gate.** Use an unfamiliar inventory schema and real migrations. Reproduce a wrong committed row and preserve an equivalent SQL edit. A workflow claiming concurrent safety must additionally exercise controlled interleavings on real connections. A team that brings its own trusted recomputation also gives us a cheap trial of the reconciliation product.

The hands-on studies demonstrate mechanisms on finite fixtures. They establish neither adoption nor market size. The open decision is whether the ordinary developer comes back for a saved business guarantee, a question answered about live code, or a patch they can merge. Those three outcomes justify meaningfully different futures for Pud.
